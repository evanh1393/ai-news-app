The 60-second answer

If an interviewer says "tell me about a project you built", this is the spoken version. Each sentence links to the section that covers it in depth.

eh-ai-blast.app is a daily AI-news briefing site. An LLM agent (Grok Bot) researches the day's AI news and writes a structured markdown briefing to a Google Drive folder. My system pulls those files every hour, validates them strictly, and loads them into SQLite, and a SvelteKit app serves them as pages, full-text search, and a read-only JSON API.

It runs on a single DigitalOcean droplet that accepts no inbound connections. Public traffic comes in through a Cloudflare Tunnel, CI deploys over a second tunnel behind Cloudflare Access, and I SSH in over Tailscale. All of it is defined in Terraform.

The workload is split into two locked-down containers: an ingest job that can reach Google and write the database, and an app that can only read the database and can't open a single outbound connection. They share one volume, and ingest swaps in a verified copy of the DB with an atomic rename, so readers never see a half-written file and the app never needs a restart.

Every merge to main builds both images, pushes them to GHCR by commit SHA, and deploys: migrations run first, then the app is replaced and has to pass its healthcheck. The guiding idea throughout is least privilege, with each layer still safe if the one in front of it fails. The LLM's output is treated as untrusted input all the way from parser to CSP.

What the product is

A reader sees a daily briefing of AI news (new models, research, policy, outages), grouped into sections, each story with its citation links. The pipeline behind it:

Grok Bot (upstream, not in this repo) runs each morning. It reads sources.md (its list of sources and query templates) from the Drive folder and writes briefing-YYYY-MM-DD.md. It can re-run during the day, which is why ingest runs hourly as well as at 08:00 ET.
The contract is a markdown format. Title heading, a coverage line, intro, an outage summary, then ## sections of numbered items, each with a bold headline and trailing citation links. ingest/briefing-md.js enforces it strictly. If a file doesn't match, it's rejected rather than loaded with guesses.
Pages: / (latest briefing) · /briefing/[date] · /archive (paginated) · /search (FTS5) · /sources (rendered from sources.md) · /notes (long-form explainers, e.g. reading AI benchmarks).
API: read-only JSON under /api/v1 (briefings list, latest, by date, search, sources). Every field is plain text, never markdown or HTML, and links are {label, url} data, so API consumers can't be handed injected markup either.

The runtime shape in 30 seconds

app (SvelteKit on adapter-node) serves the site on port 3000 inside Docker. It opens /data/briefing.db read-only on every request. It's on an internal-only network, so it can't open connections out to anything.
cloudflared (container) holds an outbound tunnel to Cloudflare. Cloudflare sends requests for eh-ai-blast.app down that tunnel, and cloudflared forwards them to http://app:3000. The host publishes no ports.
ingest is a run-once container. A host systemd timer starts it every hour (and at 08:00 ET). It pulls markdown from Google Drive, builds a new copy of the DB, checks it, and swaps it in atomically.
Deploys: on a merge to main, CI builds both images and pushes them to GHCR tagged with the short SHA. CI then SSHes in through a second tunnel on the host (behind Cloudflare Access) and runs deploy/deploy.sh, which pulls the images, runs ingest, then runs compose up --wait.

The data layer: from markdown to SQLite

The database is the boundary between the two halves of the system. Ingest is its only writer, and the app only reads it. Here is how its contents are shaped and why.

The app layer

SvelteKit with adapter-node: server-rendered pages plus API routes, built into a standalone Node server (build/). The whole server side is read-only, and it has no logins, sessions or user writes.

Reading the DB: one connection per request

src/lib/server/db.ts wraps every query batch in withDb(), which opens SQLite readonly with fileMustExist, runs Drizzle queries, and closes it. Opening a small SQLite file costs microseconds, and it's what makes the atomic swap work: a long-lived handle would keep reading the old inode after a rename.

Drizzle is used as a typed query builder only (drizzle-kit was removed). The schema source of truth is the SQL migrations, and a test checks schema.ts against them.

Routes and loaders

Each page has a +page.server.ts loader that calls a function in db.ts (getBriefing, listBriefings, search…). Offset pagination (src/lib/pagination.ts) for the archive. /api/v1/[...rest] catches unknown API paths and returns a JSON 404 instead of an HTML page.

Caching

API responses: a day older than the latest briefing can't change any more, so it's cached for a day. Everything else is cached for 5 minutes, matching the hourly ingest. Cloudflare sits in front and compresses responses.

Security headers + CSP

hooks.server.ts sets HSTS, nosniff, referrer-policy, permissions-policy (camera/mic/geo/payment/usb off), COOP. vite.config.ts sets a nonce-based CSP: default-src 'self', no third-party scripts, connect-src 'self' (an injected script couldn't send data anywhere), frame-ancestors 'none'. Static assets skip the hook, so Cloudflare adds nosniff to those responses at the edge.

Bounding the cost of public input

Search is the only route whose cost depends on what the user types. search-query.ts caps it at 200 characters / 8 words (400 otherwise), shared by /search and /api/v1/search. Cloudflare's single Free-plan rate-limit rule covers the same paths: 20 requests / 10 s per IP.

Version in the footer

Every build stamps its commit (gitVersion() in vite.config.ts, or APP_VERSION in Docker builds, which have no .git). You can confirm a deploy just by looking at the footer. -dirty marks a laptop build with uncommitted changes.

Testing

npm test = node:test for ingest (parser, DB writes, every migration on an empty DB + verify(), schema.ts vs real tables), then Vitest for the app (lib, db.ts, route loaders, API handlers) against a fixture database built from the migrations, never the real one. npm run check type-checks the TS and the plain-JS ingest via checkJs + JSDoc.

Local dev

npm run dev reads data/briefing.db. If it's missing, predev pulls a copy from the droplet's volume over SSH and runs a quick_check on it. Dev doesn't use Docker. Step 5 of the containerize plan (dev via compose) was skipped as not worth it yet.

The two images

Both start from node:26-alpine and are built from the repo root. The app image uses a three-stage build, so the final image has no Vite, Svelte, TypeScript or source code, just build/ and the production node_modules. Ingest is a single stage because it runs plain JS straight from source.

Why a separate deps stage instead of pruning in build? It's a fresh npm ci --omit=dev, so no dev packages can leak through, and Docker caches it independently. It only rebuilds when the lockfile changes, not when you edit a Svelte file.

Build context: what each image can see

Both builds use the repo root as their context. The repo root also holds data/briefing.db, .env and Terraform state, none of which belongs in an image. Each image has an allow-list ignore file that starts with * (ignore everything) and opts specific paths back in. ingest/Dockerfile.dockerignore is picked up automatically because it sits next to that Dockerfile (BuildKit looks for <Dockerfile>.dockerignore).

How ingest updates the DB without the app noticing

The app and ingest share one named volume, ai-news-app_data, mounted at /data, read-only for the app and read-write for ingest. Ingest never writes to the live file. It works on a copy and swaps it in with rename(), which is atomic on a single filesystem. Code: commit() in ingest/pull.js and migrate/verify in ingest/apply.js.

The app half of this trick is in src/lib/server/db.ts: withDb() opens a new read-only connection for each query batch and closes it afterwards. A long-lived connection would keep reading the old inode forever after a rename. Opening a new one each time means the next request after a swap sees the new file.

Infrastructure as code, and the network model

infra/ is Terraform for two providers: DigitalOcean (the droplet and its firewall) and Cloudflare (DNS, both tunnels, Access, edge rules, bot settings). What happens inside the box is handled by deploy/provision.sh (run once) and deploy/deploy.sh (every deploy). Terraform owns the resources around the droplet, not its contents.

Why tunnels instead of opening 80/443?

With no listening public ports there's nothing to scan or attack directly, the origin IP stays hidden, and TLS certificates are handled by Cloudflare. The only cost is that Cloudflare sits in the request path, which this site uses anyway for DNS, caching and rate limiting.

Why two tunnels?

The cloudflared container can only reach Docker networks, not the host's loopback sshd. Keeping SSH on a separate host-level tunnel also means the public web connector can never be turned into a path to a shell.

What lives in Terraform state?

Tunnel tokens and the Access client secret, marked sensitive and read with terraform output -raw. The state file stays local in infra/ and is excluded from both Docker build contexts. lifecycle.ignore_changes = [image, ssh_keys] on the droplet keeps an image update from forcing a replacement.

Supply chain in CI

Actions pinned to commit SHAs (Dependabot bumps them). cloudflared downloaded at a fixed version and checked with sha256. persist-credentials: false on checkout. Deploy secrets live in a GitHub environment (production) so only the main-branch deploy job sees them, and that job runs no npm code.
